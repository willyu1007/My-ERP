# Requirements

## Conclusions (read first)
- **Project**: My-ERP — 可嵌入 **My-Chat 生态**的、面向未来的**智能化 ERP 平台**（模块化/可插拔）；**财务是第一个模块**，后续逐步扩展（采购、库存、销售、HR 等）。
- **v1 聚焦**: **财务模块**，服务对象 = **会计（总账核算）** + **出纳（资金管理）**。
- **关键前提（个人生态做财务的特别约束）**: My-Chat 个人优先，而财务天生是「组织 + 多角色 + 职责分离」。因此 v1 将财务定位为**组织/团队级能力**：数据库即组织级，账套**仅属于组织/团队**，个人以成员身份进入（DP22）。
- **加入与权限（DP25）**: 组织成员**仅限邀请制**（管理员/主管邀请 → 经 Logto 接受 → 入组织并授角色），**禁止自助加入**；严格权限管理（RBAC + 最小权限 + 账套级隔离 + 操作级授权）。
- **交互/编排模型（DP26）**: 系统按**角色组织工作流**（每个角色一套「待办/任务」驱动的工作流），**而非单一线性「财务管道」**；底层复式记账模型不变，角色工作流作为可注册能力接入平台。
- **In-scope (MUST)**:
  - 会计：会计科目体系（内置《小企业会计准则》科目模板，DP10）、记账凭证（借贷平衡校验、审核、过账、红冲）、账簿与科目余额、会计期间与期末结账、财务报表（资产负债表 + 利润表 + **现金流量表**，DP11）。
  - 出纳：资金账户（现金/银行）、收付款单、现金/银行日记账、付款审批。
  - 主数据：账套（组织级）、往来单位（客户/供应商/员工）、币种（本位币）、会计期间、**现金流量项目**、辅助核算维度（**往来单位 + 部门 + 项目**，DP14）。
  - 核算运作：**期初建账**（启用期间 + 期初余额录入/导入，DP27）、收付款单按规则**自动生成凭证草稿**（DP28）、**可配置多级+金额阈值审批**（DP29）、凭证/账簿/报表**导出(Excel/PDF)+打印+凭证导入**（DP30）。
  - 智能化试点：**票据 OCR → 凭证预填**（DP12，复用 My-Chat `packages/llm` 通义/Dashscope 或视觉 OCR）。
  - 集成：复用 Logto SSO 身份与组织/成员；关键事件经 outbox 推送 My-Chat 通知；审批在 ERP 后台完成（DP9）。
  - 平台底座：模块注册与能力扩展机制（finance 为首个注册模块），预留后续 ERP 模块接入点。
- **Out-of-scope (OUT)**:
  - 非财务 ERP 模块（采购/库存/销售/生产/HR）的业务实现（仅预留架构与接入点）。
  - 直连银行/支付网关**自动划款**（v1 仅登记、审批、对账，不实际出款，DP5）。
  - **银行对账**（移至 v1.1，DP8）、工资核算、税务申报、合并报表、外币与汇兑损益。
  - 把财务明细喂入 My-Chat 的 RAG/知识库/论坛/个性化（强隔离，DP24）。
  - 原生移动 App（v1 以 Web 后台 + My-Chat 通知为交互面）。
- **Primary users**: 会计、出纳、财务主管、管理员、**只读查看者（审计/查账）**（DP13）。
- **Top user journeys**: 出纳收付款与审批；会计制单—审核—过账；期末结账与出报表；票据 OCR 预填凭证。

## Goals (MUST)
- 为会计提供合规、可审计的**总账核算**闭环：建科目 → 制单 → 审核 → 过账 → 账簿/余额 → 期末结账 → 报表。
- 为出纳提供**资金管理**闭环：资金账户 → 收付款单 → 审批 → 日记账。
- 以**独立服务 + 独立 Postgres** 形态嵌入 My-Chat：共享 Logto 身份，事件单向通知，财务数据**强隔离**于生态检索/推荐管道。
- 采用**模块化平台**架构，使财务成为可独立演进、可与未来 ERP 模块并存的第一个模块。
- 以**角色为中心的工作流**（待办/任务驱动）组织交互与编排，而非线性财务管道（DP26）。
- 以**组织级 + 邀请制 + 严格权限**为安全底座（DP22/DP25）。
- 保证**财务数据一致性、可审计性与合规留存**（借贷必平、单据可追溯、操作审计 + 会计档案法定留存）。

## Non-goals (OUT)
- 不在 v1 实现非财务 ERP 业务模块（仅保留平台扩展点）。
- 不做自动银行划款/支付通道对接。
- 不在 v1 做银行对账（移至 v1.1）。
- 不做工资、税务申报、合并报表、外币汇兑损益。
- 不把财务明细数据接入 My-Chat 生态的检索/推荐/论坛。
- 不做原生移动端。

## Users and user journeys
### User types
- **会计（Accountant）**：维护会计科目，录入/审核/过账凭证，期末结账，出具报表。
- **出纳（Cashier）**：管理现金与银行账户，登记收付款单，记现金/银行日记账。
- **财务主管（Finance Manager）**：账套与期间配置、审批、查看全局账务与报表。
- **管理员（Admin）**：组织/账套创建、成员与角色授权、系统配置。
- **只读查看者（Viewer / Auditor）**：只读查看账簿、报表、审计轨迹，不可改数据。
- 注：财务为**组织/团队级**能力，个人以组织成员身份进入（DP22）。

### Top journeys (with acceptance criteria)
1. Journey: 出纳银行付款并发起审批
   - Acceptance criteria:
     - [ ] 出纳可创建付款单（付款账户、收款往来单位、金额、用途、附件）。
     - [ ] 提交后产生「付款待审批」事件，经 outbox 推送 My-Chat 通知审批人（仅通知元数据，不含金额明细，DP24）。
     - [ ] 审批人在 ERP 后台完成通过/驳回（DP9），结果回写付款单状态。
     - [ ] 审批通过后出纳确认付款，登记银行日记账并可生成/关联记账凭证。
2. Journey: 会计录入并过账记账凭证
   - Acceptance criteria:
     - [ ] 录入时实时校验**借贷平衡**，不平衡不可提交。
     - [ ] 支持多分录、辅助核算（往来单位/部门/项目）、现金流量项目、附件与摘要。
     - [ ] 经审核（**制单人 ≠ 审核人**，DP16/DP23）后过账，更新科目余额与总账/明细账。
     - [ ] 支持对已过账凭证**红冲**，留存完整审计轨迹。
3. Journey: 期末结账与报表
   - Acceptance criteria:
     - [ ] 结账前校验本期凭证全部审核过账、无未平衡分录。
     - [ ] 可结转损益并结账；结账后该期间不可录入（除非反结账）。
     - [ ] 可生成**资产负债表、利润表、现金流量表**，与科目余额/现金流量项目一致。
4. Journey: 票据 OCR 预填凭证（试点）
   - Acceptance criteria:
     - [ ] 会计可上传票据图片/PDF，系统调用 OCR 识别关键字段。
     - [ ] 识别结果**预填**凭证草稿（金额、往来单位、摘要等），由会计确认后再保存。
     - [ ] OCR 结果与原始票据留存可追溯；识别失败可回退手工录入。

## Functional requirements (MUST/SHOULD/MAY)

Use explicit requirement strength.

### 组织、账套与多租户（DP22 / DP25）
- MUST: **账套（Ledger Book）属于一个组织/团队**（映射 Logto Organization）；一个组织可建**多账套**（DP7）。账套是数据隔离边界，数据库即组织级。
- MUST: 账套配置本位币、会计期间结构、启用年度；账套内数据严格隔离，跨账套不可越权访问。
- MUST: 个人仅以**组织成员身份**进入财务；个人 workspace 不直接持有账套。
- MUST: **成员加入仅限邀请制**（DP25）：由管理员/主管发起邀请 → 被邀请人经 Logto 接受 → 加入组织并被授予财务角色；**禁止自助加入**；支持邀请的发起/撤销/过期与状态追踪。
- MUST: **严格权限管理**：组织内 RBAC + **最小权限** + **账套级**数据隔离 + **操作级**授权（如过账、付款审批、结账为高敏操作单独授权）。
- SHOULD: 账套归档/停用与只读保留；成员离职/移除的权限即时回收与交接。

### 会计 / 总账
- MUST: **记账凭证**录入，含借贷平衡校验、审核（制单/审核分离）、过账、红冲、附件。
- MUST: **会计科目体系**，内置《小企业会计准则》科目模板，可增删（DP10）；支持多级科目与辅助核算。
- MUST: **辅助核算**：往来单位、部门、项目三维（DP14）。
- MUST: **科目余额**与**总账/明细分类账/试算平衡表**生成。
- MUST: **会计期间** = 自然年、按月 12 期 + 年结期（第 13 期），账套可设启用年度（DP31）；**期末结账/反结账**，结转损益。
- MUST: 财务报表：**资产负债表、利润表、现金流量表**（DP11）。
- SHOULD: 凭证模板/常用凭证、批量过账。
- SHOULD: 凭证分录可记录**税额（价税分离）字段**，便于后续涉税分析；v1 **不做税务申报**（DP32）。
- MAY: 报表自定义。

### 出纳 / 资金
- MUST: **资金账户**（现金、银行：开户行/账号/币种/余额）。
- MUST: **收款单 / 付款单**，关联往来单位与资金账户，状态流转（草稿/待审/已审/已收付/作废）。
- MUST: **现金/银行日记账**与账户余额。
- MUST: **付款审批流**（强 SoD：发起≠审批；单人模式可选，DP23）。
- SHOULD（v1.1）: **银行对账**与余额调节表（DP8）。
- MAY: 资金计划、额度控制。

### 期初建账、单据生成与归档（DP27–DP30）
- MUST: **期初建账**（DP27）：可设启用期间并录入/导入科目期初余额、往来期初、资金账户期初；启用期需试算平衡校验。
- MUST: **记账规则**（DP28）：收付款单等业务单据按可配置规则**自动生成记账凭证草稿**，由会计复核后过账；规则不命中可回退手工制单。
- MUST: **可配置审批策略**（DP29）：支持多级审批与按金额阈值分级，应用于付款（及可选凭证）；策略变更留痕。
- MUST: **导出/打印/导入**（DP30）：凭证、账簿、财务报表可导出（Excel/PDF）并打印归档；支持凭证批量导入（含校验与失败回执）。
- SHOULD: 导入/导出模板可配置；打印版式满足会计档案要求。

### 智能化试点（DP12）
- MUST: **票据 OCR → 凭证预填**：上传票据 → OCR 识别 → 预填凭证草稿 → 人工确认。
- SHOULD: 复用 My-Chat `packages/llm`（通义/Dashscope，合规已注册）作为模型通道；保留 generation 记录。
- MAY: AI 辅助科目建议、智能问账（后续）。

### 角色工作流（DP26）
- MUST: 系统以**角色为中心组织工作流**（每个角色一套「待办/任务」驱动的工作流），而非单一线性财务管道；每个角色工作流既在 ERP 后台呈现为「待办工作台」，也经事件向 My-Chat 推送对应角色通知。
- MUST: v1 角色工作流：
  - **出纳**：资金收付（建收/付款单 → 提交审批 → 审批通过后确认收付 → 记日记账）；待办：待提交/被驳回/待确认收付。
  - **会计**：凭证核算（制单含 OCR 预填 → 送审 → 过账 → 期末结账 → 出报表）；待办：草稿/被驳回/待过账。
  - **财务主管**：审批（待我审批：凭证审核 / 付款审批 → 通过/驳回）；待办：审批队列。
  - **管理员**：组织治理（建组织/账套 → 邀请成员 → 授角色/权限 → 期间与配置）；待办：待处理邀请/权限申请。
  - **只读查看者**：查阅（只读账簿/报表/审计轨迹，无任务动作）。
- MUST: 角色工作流以**可注册能力**形式接入平台（finance 模块注册其角色工作流），为后续 ERP 模块沿用同一注册/编排范式。
- SHOULD: 跨角色衔接通过任务流转与事件驱动（如出纳提交 → 主管待办出现），不耦合为硬编码管道。

### 集成与平台
- MUST: 通过 **Logto SSO** 完成身份认证；组织/成员来源于 My-Chat 生态。
- MUST: 关键事件（待审批、审批结果、异常/逾期提醒）经 **outbox → 事件** 发布，My-Chat 新增消费端推送通知（DP9）。
- MUST: **集成隔离护栏（DP24）**：财务明细**绝不进入** My-Chat 的 RAG/知识库/论坛 public-draft/个性化；对外仅暴露**通知元数据 + 审批回写**。
- MUST: 提供 **HTTP API** 供后台前端/My-Chat 调用；遵循 My-Chat 的 api-client/权限约定。
- MUST: 提供**独立财务后台 Web** 作为主要操作界面（DP4），审批在后台完成。
- SHOULD: **模块注册机制**，finance 为首个模块，预留后续 ERP 模块接入点。
- MAY: 接收 My-Chat 工作流触发（如对话发起付款）。

### 权限与审计
- MUST: 组织内 **RBAC**（会计/出纳/主管/管理员/只读查看者）+ **账套级数据隔离** + **操作级授权**（最小权限）。
- MUST: 成员**邀请制**加入（DP25）；离职/移除即时回收权限。
- MUST: **职责分离**：制单≠审核、付款发起≠审批；团队仅 1 人时可显式开启**单人模式**（放宽 SoD + 强制二次确认 + 全量留痕，DP23）。
- MUST: 关键操作（制单、审核、过账、红冲、收付款、审批、结账、反结账）写**审计日志**。
- MUST: **会计档案法定留存**：凭证/账簿按法规长期保存（约 30 年）、年度财报永久、月/季报 10 年（详见 NFR）。

## Data and integrations (high level)
- **Core entities**: 组织(Organization, 来自 Logto)、成员与角色(Membership/Role)、**邀请(Invitation)**、账套(LedgerBook)、会计科目(Account)、会计期间(AccountingPeriod)、**期初余额(OpeningBalance)**、记账凭证(JournalVoucher)+分录(JournalEntryLine)、**记账规则(PostingRule)**、科目余额(AccountBalance)、辅助核算项(AuxiliaryItem: 往来/部门/项目)、现金流量项目(CashFlowItem)、往来单位(BusinessPartner)、币种(Currency)、资金账户(CashAccount)、收付款单(Receipt/Payment)、现金银行日记账(CashJournal)、审批(Approval)+**审批策略(ApprovalPolicy)**、**任务/待办(Task)**、票据/OCR记录(VoucherAttachment/OcrResult)、审计记录(AuditRecord)、Outbox 事件(OutboxEvent)。
- **External systems**:
  - **My-Chat / Logto**：SSO 身份与组织/成员（身份与租户来源）。
  - **My-Chat 事件/通知**：消费 ERP outbox 事件，推送通知；审批结果可回写（仅元数据，强隔离）。
  - **OCR / LLM**：票据 OCR 与（可选）凭证辅助，优先复用 My-Chat `packages/llm`（通义/Dashscope）。
  - **PostgreSQL**（ERP 独立实例，Prisma 为 schema SSOT）。

## Constraints and assumptions
- Constraints:
  - 可嵌入 My-Chat：复用 **Logto 身份**、遵循 **Postgres + Prisma（SSOT）+ outbox/saga** 数据流、采用 **morethan** 设计语言。
  - 技术栈对齐 My-Chat：**TypeScript + pnpm monorepo + NestJS（API）+ Prisma + PostgreSQL**。
  - **独立服务 + 独立数据库**；与 My-Chat 通过 SSO + 事件解耦，不直连其数据库。
  - 财务为**组织/团队级**能力（个人生态约束，DP22）；财务数据**强隔离**于生态检索/推荐（DP24）。
  - 财务合规：借贷必平、单据不可静默删除（作废/红冲留痕）、操作全审计、**会计档案法定留存**。
  - v1 不实际划款（仅登记/审批/对账，DP5）；v1 单一本位币（DP15）。
- Assumptions:
  - My-Chat 的 Logto Organization/Membership 可作为 ERP 的组织与成员来源。
  - My-Chat 侧可新增/已有消费 ERP 事件并推送通知的能力。
  - OCR/LLM 通道可复用 My-Chat 既有合规模型（通义/Dashscope）。
  - 财务团队规模为数人~数十人并发。
